# 배울 점, 개선 방향, 다른 분야에 적용하기

[전체 동작 해설](architecture.md) · [DB](modules/database.md) · [에이전트](modules/agents.md)

아래의 현재 동작은 고정한 소스에 대한 해설이며, 개선안은 **이번 이관에서 구현하지 않은
후속 설계 제안**입니다. 한국어 주석 추가와 기능 변경을 섞지 않기 위해 분리했습니다.

## 1. 그대로 배울 가치가 있는 설계

**대상과 작업 기록의 분리.** 전역 `assets`에 같은 객체를 중복 저장하지 않고,
작업별 `exploration_nodes`에 그 객체를 관찰한 근거를 기록합니다. 이 구조는 “객체의 현재
정보”와 “누가 어떤 맥락에서 그런 결론을 냈는가”를 동시에 조회하기 좋습니다.
근거는 [db/assets.go](../../db/assets.go), [db/exploration.go](../../db/exploration.go)입니다.

**원자적인 작업 수령.** 조회한 후보가 아직 `open`일 때만 `running`으로 바꾸는
조건부 UPDATE는 단순하면서 명확합니다. 비교 후 대입(CAS) 개념을 애플리케이션의
작업 상태에 적용하는 사례입니다. 다만 외부 도구가 두 번 실행되는 문제는 별도로 다룹니다.

**영속 기록과 모델 입력의 분리.** 기록을 삭제하지 않고 현재 작업에 필요한 일부만
모델에 제공하면 비용과 설명 가능성을 함께 관리할 수 있습니다. `graph_overview`,
상세 조회 도구, cold digest의 역할을 나누어 읽어 보세요.

**버전이 있는 증거.** 원본 트래픽의 정리 수명과 보고서 증거의 보존 수명을 분리하고,
`evidence_version`으로 보고서의 근거가 바뀌었는지 확인하는 방식은 실험·감사·품질
분석에도 유용합니다. [evidence/store.go](../../evidence/store.go)가 핵심입니다.

**모델 밖의 상태 관리.** 에이전트가 대화에서 “끝났다”고 말하는 것과 DB에 결과를
커밋하는 것을 구분합니다. 작업·의도·발견·보고서의 상태를 코드로 표현할수록 재개와
사람 검토, 원인 추적이 쉬워집니다.

## 2. 우선 개선할 부분

| 우선순위 | 현재 확인한 경계 | 제안 | 완료를 판단하는 기준 |
| --- | --- | --- | --- |
| 1 | 역할마다 승인 hook 연결이 같지 않음 | 모든 실제 도구 호출을 공통 실행기로 통합 | Worker·Planner·Main·지연 도구에 같은 정책이 적용되는 테스트 |
| 1 | 자산 차단은 특정 삽입/의도 경로에 적용 | 도구·네트워크 실행 경계에서 범위 강제 | 범위 밖 요청이 실제 호출 전 거부됨 |
| 1 | DB의 fact/finding 상태만으로 의미를 검증하지 않음 | 독립 검증 상태와 근거 기준을 추가 | 가설·관찰·검증·기각이 명시적으로 구분됨 |
| 1 | goroutine은 운영체제 격리가 아님 | 작업별 실행 환경과 자격 증명·파일·네트워크 권한 분리 | 한 작업이 다른 작업의 자원을 읽거나 바꾸지 못함 |
| 2 | 외부 실행 후 중단·재개 시 중복 부작용 가능 | 도구 요청 ID·멱등 키·실행 결과 ledger | 동일 요청 재시도가 같은 외부 변경을 중복 수행하지 않음 |
| 2 | Planner todo는 메모리 상태 | 버전이 있는 영속 계획 저장 | 재시작 뒤에도 의존 순서·완료 근거 복원 |
| 2 | 일부 overview 집계는 제한 목록 길이를 사용 | 정확한 COUNT와 화면 창을 분리 | 대량 작업에서 총계·진행 상태가 누락되지 않음 |
| 2 | SSE 브로드캐스트 버퍼 포화 시 유실 가능 | 알림은 wake 신호로 쓰고 DB cursor에서 실제 기록 조회 | 느린 클라이언트·재연결에도 저장된 이벤트 복원 |
| 2 | 선택적 승인 모델의 실패 기본값이 허용일 수 있음 | 용도별 오류 정책·명시적 상태·독립 감사 | 파싱/네트워크 실패 때 의도한 보류/거부 정책 검증 |
| 3 | 의존 도구 일부가 latest 설치 | 도구 버전·이미지 digest 고정 | 같은 소스로 재현 가능한 실행 환경 확보 |
| 3 | 원본 릴리스 CI에 일반 PR 전체 검증이 없음 | 변경 영역별 문법·타입·단위·격리 통합 검증 | 실패가 main/릴리스 이전에 드러남 |

관련 코드는 [guard](../../guard/guard.go), [intercept](../../intercept/intercept.go),
[agent/assembly.go](../../agent/assembly.go), [server/engine.go](../../server/engine.go),
[server/server.go](../../server/server.go)에서 확인하세요. 예를 들어 전역 DB ID는
자연스럽게 빈 번호가 생길 수 있어 SSE 유실을 단순히 `다음 ID = 이전 ID + 1`로 판단하면
안 됩니다. 한 클라이언트의 조회 범위에 맞는 cursor 재생 계약이 필요합니다.

## 3. 단순 이름 변경보다 중요한 추상화

ARTEX의 보안 전용 자산 유형과 발견 모델을 다른 분야의 객체·관찰·결론으로 바꾸어야 합니다.
이때 전부 갈아엎기보다 아래 경계를 먼저 분리하는 편이 검증하기 쉽습니다.

| 경계 | 현재 예 | 일반화한 역할 |
| --- | --- | --- |
| 대상 저장 | 도메인·IP·서비스 | 버전이 있는 업무 객체 저장소 |
| 작업 기록 | goal·intent·fact·finding | 목표·실행 계획·관찰·결론 |
| 도구 실행 | Bash·HTTP·브라우저·MCP | 승인된 외부 작업 어댑터 |
| 근거 | HTTP 요청·응답 | 파일·로그·표·측정치와 출처 |
| 검증 | 선택적 재검증 Agent | 도메인별 규칙·독립 측정·사람 판정 |
| 컨텍스트 | overview·node_detail·digest | 현재 작업에 필요한 근거 선택 |
| 정책 | 범위·도구 승인 | 객체별 권한·부작용 제한·승인 |
| 화면 | 자산·탐색·증거 | 대상·진행·검토·재현 UI |

핵심은 `ObjectStore`, `TaskStore`, `EvidenceStore`, `ToolExecutor`, `Policy`, `Verifier`
같은 책임 경계를 잡는 것입니다. 이름은 설계 제안이며 현재 코드에 이 인터페이스가
이미 있다는 뜻이 아닙니다.

## 4. 다른 분야에 적용하는 구체적인 대응

| 분야 | ARTEX 자산에 대응하는 객체 | intent/도구 예 | 근거와 검증 |
| --- | --- | --- | --- |
| 소프트웨어 품질 분석 | 저장소·커밋·모듈·테스트 | 실패 재현, 로그 비교, 영향 범위 조사 | 커밋 고정 로그·테스트 결과·독립 재실행 |
| 오디오/DSP 품질 | 장치·펌웨어·샘플·필터 | 주파수 응답 측정, 기준 음원 비교 | 원본 오디오·측정 조건·수치 오차 기준 |
| ERP 오류 원인 분석 | 주문·전표·거래처·처리 단계 | 읽기 전용 조회, 불일치 후보 추적 | 원장 스냅샷·SQL·정산 규칙 |
| 제조 품질 | 설비·LOT·공정·검사 항목 | 원인 가설 비교, 센서 시계열 조회 | 교정 정보·측정 데이터·공정 검증 |
| 연구 문헌 정리 | 논문·주장·실험·데이터셋 | 근거 수집, 주장 비교, 재현 계획 | 원문 위치·실험 조건·상충 근거 |
| 고객지원 분석 | 제품 버전·티켓·오류 유형 | 사례 분류, 재현 조건 확인 | 원문 티켓·환경 정보·해결 확인 |

예를 들어 DSP 품질에서는 `root_domain → subdomain → service` 계층을 그대로 쓰지 않고
`제품 → 펌웨어 버전 → 시험 조건 → 측정 실행` 관계로 바꿉니다. `finding`은 취약점 대신
“기준 대비 주파수 응답 편차” 같은 품질 결론이 되고, HTTP 증거 대신 WAV와 측정 표를
보관합니다. LLM은 다음 측정을 계획하고 측정 도구는 수치를 만들며, 최종 통과 여부는
고정한 오차 기준으로 계산해야 합니다.

ERP에서는 일단 읽기 전용 어댑터로 시작하는 편이 좋습니다. 모델이 만든 SQL을 그대로
원장 수정에 사용하는 구조보다, 조회 결과를 근거로 제안하고 별도의 승인된 업무 API가
수정하도록 분리하면 재현과 감사가 쉽습니다.

## 5. 작은 검증부터 진행하는 확장 순서

1. 한 가지 대상 유형과 하나의 결과를 고릅니다. 예: 특정 커밋의 테스트 실패 원인.
2. 객체 ID에 버전·관찰 시점을 포함해 과거와 현재를 구분합니다.
3. 읽기 전용 도구와 근거 파일 저장을 먼저 연결합니다.
4. Planner가 만든 결론을 규칙 기반 검증기 또는 독립 재현으로 확인합니다.
5. 사용자가 근거를 따라 확인할 수 있는 화면을 만듭니다.
6. 중단·재시도·중복 결과·오래된 증거·상충 관찰을 시험합니다.
7. 이 흐름이 안정된 뒤 더 많은 작업과 쓰기 권한을 확장합니다.

## 6. 한국어 지원을 기능으로 확장하려면

이번 작업은 문서와 주석을 한국어화했습니다. 실제 제품 언어 전환은 별도 기능입니다.
후속 작업에서는 UI 문자열을 번역 키로 분리하고, 날짜·숫자·상태 표시를 locale에 맞추며,
프롬프트의 출력 언어와 도구 JSON 식별자 계약을 분리해야 합니다.

프롬프트를 번역하면 모델 행동도 달라질 수 있어 “뜻이 비슷하다”만으로 충분하지 않습니다.
동일한 고정 입력에 대해 도구 선택·JSON 유효성·근거 누락·승인 준수·토큰 사용량을
비교해야 합니다. 외부 SDK의 한국어 검색 처리도 실제 연결하는 경로에서 따로 검증하세요.
