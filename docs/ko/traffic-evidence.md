# 발견 사항에 연결하는 다중 HTTP 증거

[한국어 문서 안내](README.md) · [지원 서비스](modules/services.md)

원본 [漏洞流量证据.md](../漏洞流量证据.md)의 한국어 번역·해설입니다.
도구·API 이름과 ID의 의미는 원본 계약을 유지합니다.

## 1. 사용 흐름과 자동 바인딩 설정

발견 상세 화면의 연결 트래픽에서는 여러 페이지에 걸친 다중 선택, 증거 용도·설명,
순서 변경, 연결 해제를 지원합니다. 트래픽 화면에서도 여러 기록을 골라 기존 발견 하나에
연결할 수 있습니다. 다른 작업에서 상속한 발견의 증거는 읽기 전용이며 수정은 원본
작업으로 이동해 수행합니다.

설정의 **Agent 자동 트래픽 바인딩**은 기본 OFF입니다. `/api/settings`의
`agent_traffic_binding`으로 읽고 변경합니다. 활성화하면 요청·응답 확인과 도구 호출,
추가 프롬프트에 따른 토큰 사용이 늘 수 있습니다. 다음 Agent 실행부터 새 설정을 사용합니다.
OFF일 때는 자동 바인딩 인자·도구·지침을 감추고 이미 실행 중인 세션의 새 자동 연결도
거부합니다. 수동 연결, 캡처 설정, 기존 증거 읽기·내보내기는 별개입니다.

활성화한 기본 흐름은 **발견 저장 → 보고서 Agent 시작 → 실제 트래픽 확인·연결 →
최신 증거 버전으로 보고서 저장**입니다. 보고자는 `evidence`에 검증 명령·주요 출력·이미
알고 있는 실제 트래픽 ID와 용도를 남깁니다. 보고서 Agent는 발견 상세와 실행 기록을 읽고
`traffic_search`/`traffic_get`으로 확인한 뒤 `bind_finding_traffic`을 호출합니다.
OFF인 보고서 Agent도 사람이 연결한 스냅샷을 읽고 보고서를 작성할 수 있습니다.

기존 호출과의 호환성을 위해 `report_finding`의 `traffic_refs`와 `evidence_hint_id`로
즉시 명시 연결하는 경로도 있습니다. HTTP가 아닌 관찰이나 캡처가 없는 상황은 참조 없이
보고할 수 있습니다. 그 경우 명령 출력·로그 같은 다른 검증 가능한 근거를 남깁니다.
없는 트래픽을 만들거나 불확실한 ID를 추측하여 넣는 기능은 아닙니다.

제출한 ID는 모두 유효하고 본문이 온전해야 합니다. 한 항목이라도 실패하면 연결 묶음을
롤백합니다. 발견 보고와 함께 연결하다 실패하면 발견 보고도 함께 롤백합니다.
동일 스냅샷의 중복 추가는 연결 수를 늘리거나 기존 설명을 덮어쓰지 않습니다.

## 2. 증거의 용도

```json
{
  "traffic_refs": [
    {"traffic_id": "실제로 확인한 ID", "role": "baseline", "note": "정상 동작 대조 요청"},
    {"traffic_id": "다른 실제 ID", "role": "proof", "note": "관찰을 뒷받침하는 요청"}
  ]
}
```

배열 순서가 초기 증거 순서입니다. `baseline`은 정상 대조, `proof`는 발견 근거,
`verification`은 추가 검증, `supporting`은 보조 증거이며 기본값입니다.
도메인과 시간은 후보를 찾는 조건일 뿐, 기록이 특정 작업에서 나왔다는 자동 판정 근거가
아닙니다. 원문의 프롬프트 참고 출처인
[CyberStrikeAI 도구 지침](https://github.com/RuoJi6/CyberStrikeAI/blob/54d56774b8bd285817d16d48b70a4a5e6e0963f7/internal/app/vulnerability_tools.go)
표기도 보존합니다.

## 3. 가장 중요한 두 ID와 버전

`report_finding`의 첫 줄은 기존과 같이 `finding recorded: <탐색 노드 ID>`입니다.
뒤의 JSON에는 독립 발견 레코드 `finding_id`, 탐색 노드 `finding_node_id`, 연결 요약이
포함됩니다. 같은 발견을 나타내더라도 두 ID가 같은 숫자라고 가정하면 안 됩니다.

| 도구/기능 | 사용하는 ID·버전 |
| --- | --- |
| `get_finding_traffic(finding_id)` | **독립 발견 레코드 ID**, 정렬된 목록과 `version` 반환 |
| 부분 본문 읽기 | `binding_id`, `side=request\|response`, `offset`, `length`, 최대 8192바이트 |
| `update_finding_report`의 `finding_id` | 호환성상 **탐색 노드 ID**를 계속 사용 |
| `update_finding_report.evidence_version` | 실제로 읽었던 증거 버전 |
| `bind_finding_traffic(finding_id, traffic_refs)` | 기존 발견에 추가 연결, 발견을 다시 등록하지 않음 |

보고서를 생성하는 동안 증거가 바뀌면 과거 버전으로 저장하는 요청을 거부하고 다시 읽도록
합니다. 버전 없이 저장한 오래된 호출은 기존 트래픽 증거를 모두 반영했다고 주장하지 않습니다.
연결·설명·용도·순서가 달라지면 기존 보고서는 갱신 필요 상태가 됩니다.

자동 연결이 켜져 있으면 `add_hint`/`add_task_hint`의 단일 또는 배열 힌트에도
`traffic_refs`를 저장할 수 있습니다. Planner의 `evidence_hint_id`는 현재 작업의 특정
힌트를 명시 선택하며 상속 힌트는 대상이 아닙니다. 실패한 보고는 부분 발견을 남기거나
보고서 Agent를 먼저 시작하지 않습니다.

조회 도구 `list_findings`, `list_task_findings`, `node_detail`, `get_task_node_detail`은
명확한 `finding_id`와 `finding_node_id`를 제공합니다. 기존 `id`의 탐색 노드 의미는 유지합니다.
서버 시작의 호환 마이그레이션은 선택적 schema 속성을 보강하며 사용자의 도구 목록·프롬프트·
설명·활성 설정을 유지합니다. 플랫폼 대화에 작업 맥락이 없으면 작업 Agent에 구조화된
힌트로 기존 근거를 전달하는 흐름입니다.

## 4. REST API

기본 주소는 `/api/exploration/findings/{finding_id}/traffic`이며 **독립 발견 ID**를 씁니다.
기존 인증을 적용하고 `context_task`로 작업 가시성과 상속 읽기 전용 상태를 검사합니다.

| 메서드 / 상대 경로 | 요청 또는 결과 |
| --- | --- |
| `GET` | 정렬된 요약, 증거 버전, 보고서가 사용한 버전 |
| `POST` | `{"traffic_refs":[...]}` 전체 묶음 추가 |
| `PATCH /{binding_id}` | `{"version":1,"role":"proof","note":"설명"}` |
| `DELETE /{binding_id}` | `{"version":1}` |
| `PUT /order` | `{"version":1,"binding_ids":["2","1"]}`, 전체 목록 필요 |
| `GET /{binding_id}` | 스냅샷 메타데이터와 제한된 미리보기 |
| `GET /{binding_id}/body` | `side/offset/length`, `download=1`이면 전체 원본 바이트 |

버전·순서 집합 충돌과 보관 중 쓰기는 `409`, 상속 데이터 수정은 `403`, 없는 연결 또는
해당 발견에 속하지 않는 연결은 `404`입니다. 첨부 읽기·무결성 검사 실패는 명시적인 오류입니다.

## 5. 저장과 일관성

PostgreSQL 시작 마이그레이션에 `traffic_evidence_snapshots`, `finding_traffic_bindings`,
`findings.evidence_version`, `report_evidence_version`을 추가합니다. 새 버전 필드 기본값은
0이며 과거 설명 문장을 추측하여 트래픽을 자동 연결하지 않습니다.

스냅샷은 원 트래픽 ID, 수집 시점, URL, 메서드, 상태 코드, 헤더, 본문 길이, SHA-256을
저장합니다. 본문은 `<data>/evidence/blobs/<앞 두 글자>/<hash>.bin`에 보관합니다.
여러 발견이 같은 스냅샷·본문을 공유할 수 있고 원 트래픽의 수명과 분리합니다.
내용 변경 API는 없으며 해시가 다르면 읽기·내보내기를 실패시킵니다.

원 트래픽 잠금 아래 전체 본문을 읽고, 파일을 먼저 영속화·검증한 뒤 하나의 PostgreSQL
트랜잭션에서 탐색 노드·관계·발견·스냅샷·연결을 기록합니다. 커밋 뒤에만 계획자에게
알립니다. 실패하면 참조 없는 파일이 남을 수 있으나 부분적인 업무 기록은 남기지 않습니다.

advisory lock `7337741004`가 증거 파일과 SQL 참조를 조정합니다. 작업 행 잠금은
보관 대기 이후의 증거 수정을 막습니다. 복원은 본문 설치부터 메타데이터 커밋까지 증거
잠금을 유지합니다. 발견 삭제 시 관련 연결은 연쇄 제거됩니다.

정리기는 매시간 실행하며 미참조이면서 진행 중 작업이 사용하지 않는 내용을 최소 24시간
유예 후 회수합니다. 일반 트래픽 정리는 증거 디렉터리를 지우지 않습니다. 백업은 DB와
`data/evidence`를 함께 고려해야 합니다.

## 6. 내보내기와 작업 보관

Markdown은 정렬된 증거와 버전, JSON은 메타데이터, CSV는 연결 수와 ID를 포함합니다.
`md-zip`에는 발견 Markdown과 아래 파일이 들어갑니다.

| 경로 | 의미 |
| --- | --- |
| `evidence/<finding_id>/<binding_id>/manifest.json` | 스냅샷 메타데이터 |
| 같은 위치의 `request.http`, `response.http` | 읽을 수 있는 요청·응답 |
| 같은 위치의 `request.bin`, `response.bin` | 원래의 바이너리 본문 |

다운로드 응답 전에 첨부 복사·해시 검사·압축·디스크 동기화·ZIP 항목 CRC 읽기 검사를
수행합니다. 첨부가 없거나 손상되면 전체 다운로드가 실패합니다.

보관 v3은 발견 연결 관계로 증거를 수집하고, 패키지를 검증한 뒤 활성 데이터를 정리합니다.
공유 증거는 남깁니다. 복원은 본문 검사·설치 후 메타데이터를 트랜잭션으로 복구합니다.
v1/v2 복원도 유지하며 새 필드가 없으면 0을 명시합니다.

## 7. 원문이 제시하는 검증 범위와 한계

원문은 패키지별 전용 PostgreSQL, Go 관련 테스트와 race 검증, 프런트 타입 검사와 정적
빌드, 독립 포트·로컬 HTTP/HTTPS 대상의 종단 검증을 안내합니다. 이것은 기능 검증 안내이며
이번 한국어판 작성에서 해당 실험을 모두 수행했다는 뜻이 아닙니다.

초기 설계는 전역 증거 조정 잠금을 사용하므로 대량 연결·내보내기·느린 첨부 읽기가 다른
증거 작업을 기다리게 할 수 있습니다. 없는 기록이나 불완전 본문을 보충 생성하지 않습니다.
이 기능은 캡처 ON/OFF나 HTTPS IP 직접 접속 인증서 문제를 바꾸지 않습니다.
